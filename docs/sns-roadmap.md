# SNS化ロードマップ（TODO）

えらぶノートを「自分の記録帳」から「好きなものをみんなと共有できるアプリ」に広げるための TODO。
X のように、自分のページでは自分の持ち物（評価・レビュー）だけを見られ、タイムラインではみんなの口コミを見られる形を目指す。

## 決定事項（2026-10-06 時点）

| 論点 | 決定内容 |
|---|---|
| 商品の持ち方 | 共通の **商品（products）** と、個人の **持ち物（items）** に分ける。商品は検索して選び、なければ自分で登録する |
| 画像 | 商品は代表画像を持つ。持ち物は自分の画像を任意で持つ。表示は「自分の画像 → なければ商品の代表画像」の順 |
| 商品情報の編集権限 | 最初に登録した人だけが編集できる |
| カテゴリ | 商品には運営が用意した **共通カテゴリ** をつける。今の個人カテゴリは自分の持ち物の整理用に残す |
| 公開範囲 | 持ち物ごとに公開スイッチを持つ。**初期値は非公開** |
| MVP のソーシャル機能 | いいね / フォロー / 気になる（保存） |
| LINE 通知 | 定期まとめ通知（例: 毎週、なくなりそうな持ち物の一覧を送る） |

## 未決定事項（後で決める）

## Phase 1: 商品（products）と持ち物（items）の分離

一番大きな作り変え。ここが固まらないと後の機能が作れないので最初にやる。

### DB
- [ ] `common_categories` テーブル（共通カテゴリ）を作成し、seed で初期データを投入
- [ ] `products` テーブルを作成
  - `name`, `brand_name`, `capacity`, `capacity_unit`, `common_category_id`, `created_by_id`（users への FK）
  - 代表画像は Active Storage（`has_one_attached :image`）
  - 検索用に `name` / `brand_name` へインデックス
- [ ] `items` に `product_id` を追加（移行が終わるまでは null 許可）

### データ移行（既存データを壊さないよう段階的に）
- [ ] 既存の items から products を作るデータ移行タスクを作る（rake タスク推奨。再実行しても重複しないようにする）
  - 商品名 + ブランド名が同じものは同じ product にまとめる
  - 作成者（`created_by_id`）は、その items の持ち主にする
  - 既存の画像は **持ち物側の画像のまま残す**（勝手に共通の代表画像にしない）
- [ ] 本番相当のデータで移行を試し、件数が合うことを確認する
- [ ] 移行後に `items.product_id` を NOT NULL にする
- [ ] items から `name` / `brand_name` / `capacity` / `capacity_unit` を削除する（**画面がすべて product 参照に切り替わってから**、別のマイグレーションで行う）

### Model
- [ ] `Product`: バリデーション、`belongs_to :created_by`、`has_many :items`、`editable_by?(user)`
- [ ] `Item`: `belongs_to :product`、表示用画像を返すメソッド（自分の画像 → 商品画像の順）
- [ ] 容量あたりのコストの計算元を `product.capacity` に変更
- [ ] ゲストのサンプルデータ（`User#seed_guest_sample_data!`）を products 対応にする

### Controller / View
- [ ] 持ち物登録フォームを「商品を検索して選ぶ → なければ新規登録」の流れに変更
- [ ] オートコンプリートを products 検索に変更（自分の持ち物ではなく、全商品が対象）
- [ ] 商品情報の編集画面（登録者だけが開けるようにする）
- [ ] 一覧・詳細・ホーム・レビュー画面の表示を product 参照に変更

### テスト
- [ ] Product モデルのテスト（バリデーション、編集権限）
- [ ] データ移行タスクのテスト（同じ商品がまとまること、再実行しても増えないこと）
- [ ] 他人が商品を編集できないこと（controller テスト）

## Phase 6: LINE 定期まとめ通知

今の LINE 連携は「LINE ログイン」だけで、メッセージ送信には別途 **Messaging API**（LINE 公式アカウント）の準備が必要。

### 事前準備・調査
- [ ] LINE Developers で Messaging API チャネルを作成（**今の LINE ログインチャネルと同じプロバイダー** にする。違うプロバイダーだとユーザー ID が一致しない）
- [ ] ユーザーに公式アカウントを友だち追加してもらう導線（友だちでないと送れない）
- [ ] 無料プランの月間送信数の上限を確認し、まとめ通知の頻度を決める
- [ ] 定期実行の方法を決める（候補: Render Cron Job / GitHub Actions の schedule / Solid Queue の定期ジョブ）。ゲストアカウントの削除（`guest:cleanup`）の定期実行とまとめて決める

### 実装
- [ ] `users` に通知設定（例: `line_notify_enabled`）を追加し、設定画面でオン/オフできるようにする
- [ ] 送信処理をサービスクラスまたはジョブにまとめる（例: なくなりそうな持ち物が1件以上あるユーザーに一覧を送る）
- [ ] 定期実行の設定
- [ ] 送信失敗時のログ出力（ブロックされた、など）
- [ ] テスト（LINE API はスタブにする）
