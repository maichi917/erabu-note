# 設計の原則と判断の記録

えらぶノートで機能を足すか・やめるかを決めるときの基準と、これまでの判断をまとめたもの。
新しい機能を考えるときは、まずこの原則に照らす。

## 原則

1. **主役は感想**
   えらぶノートは、選ぶための感想を溜めて見返すアプリ。在庫管理はメインではなく、感想を見返すきっかけを作るためのサブ。
2. **入力は最小限**
   手間に見合う見返りがない入力は求めない。記録が続かないと、感想も溜まらない。
3. **予測はしない**
   使い切りの時期などは、使っている本人が一番よく分かる。消費のペースは不規則で、アプリの予測は一番欲しい場面ほど外れる。

## やらないこと

| やらないこと | 理由 |
|---|---|
| 使い切り予測、使用期間の記録 | 原則3。日付を正しく取るには使い始めの記録も必要になり、原則2にも反する |
| 在庫数の管理 | 原則1・2。正確に更新し続けるのが負担で、続かない |
| 使用履歴（使い始め・使い終わり）の管理 | 原則2。選ぶ判断に役立たず、開始・終了の操作の手間だけが残る |
| 感想の履歴（使うたびの感想、値段の変化） | 原則2。感想は1つを上書きし、今の気持ちを残す |

## 一度作って、削除した機能

| 削除した機能 | 削除した時期・issue | 削除した理由 | 代わりにしたもの |
|---|---|---|---|
| 使用頻度、1回あたり・1日あたりのコスト | 2026-08（#286） | 日によって違うものを使う、1日に何度も使うなど、実際の不規則な使い方に合わず、計算の精度が低い | 容量あたりのコストだけ残した |
| 平均評価 | 2026-08（#286） | 感想を時系列で見返す設計に統一したため | 感想は1つ（上書き） |
| 使い切り予測と購入リマインダー（メール） | 2026-08（#286、#68） | 予測が一番欲しい場面ほど精度が低い、という構造的な問題 | なくなりそうのフラグ（手動） |
| 使用中止の理由（使い切った／途中でやめた） | 2026-08（#286） | 感想が主役なので、星評価とレビューで表せると判断 | 感想 |
| 在庫数 → 在庫あり/なし | 2026-08（#286 で2択にし、#297 で廃止） | 正確に更新し続けるのが負担で、続かない | 手放す（アーカイブ） |
| 使用中の状態と使用履歴（開始日・終了日） | 2026-08（#297） | 選ぶ判断に役立たず、開始・終了ボタンの手間だけが残る | よく使うもの。感想は items が直接持つ |

どれも「精度が出ない」か「入力の手間に見合わない」という理由で削除している。上の原則は、この経験から生まれたもの。

## これからの予定

### issue の作り方

修正のあとにやることも、**中身を詰めずに issue だけ先に作り、GitHub Projects に入れておく**（2026-10-15 に決定）。

- **理由**：Project を見れば、次に何をやるか・そのあとに何が控えているかが一目で分かるようにするため。予定が docs にしかないと、どの issue から手をつけるか分かりにくかった
- **先に書くこと**：概要（何をやるか）、検討中のこと、関連する docs へのリンクだけ
- **あとで書くこと**：「やりたいこと」と「完了条件」は、着手するときに詰める。修正を進めるうちに考えが変わることがあるため
- **Project の Status**：すぐやるものは Todo、先の予定と検討中のものは Pending
